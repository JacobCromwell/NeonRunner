# Questions from I1 (shader cleanup in every zone)

## 1. Split the street shader per zone? (performance; no GDD section)

**The question.** `kit_solid.gdshader` (the street's lit surfaces: every wall, floor, ceiling, doodad and rubble piece)
carries the surface patterns of every zone: the Marketplace's, Corporate's, the Dead Zone's, the Golden Zone's and
Palace's, the Casino's and the Beach's, about 164 k of its 196 k characters of code. Each of its 8 programs is 319 k
characters with the engine's own, and a zone uses 0 to 45 k of those patterns. It is by far the biggest program in
every zone: 8 of a level's 130 to 213 programs, 11 to 17% of a load's characters of shader code (the solid numbers).
Measured by wrapping the other zones' includes and dispatch lines in an `#ifdef` that is never defined (an experiment
on a copy, not built; the City needs only the base patterns, the shared marks and the cult's emblem, the Beach its
own, the Palace the Golden Zone's and its own), the web export's load in software WebGL:

| level | street shader's programs | characters of shader code linked | compiler wait (rough, see below) |
|---|---|---|---|
| City 1 | 319 k -> 162 k characters each | 15.1 -> 13.8 M (-9%) | 15.6, 15.3, 15.5 s -> 5.8, 8.2, 5.5 s |
| Beach 1 | | 19.8 -> 19.0 M (-4%) | 19.1 s -> 8.1 s |
| Golden Palace | | 25.3 -> 24.3 M (-4%) | 16.5 s -> 7.5 s |

The number of programs is the same. **The wait is a rough number**: a browser defers compiles, so the time of a
program is charged to whichever call asks for its result first and includes what was queued ahead of it, and software
WebGL is not Direct3D. It pointed the same way in every run (the street shader's programs were the largest share of
the wait, and the trial cut it by about half or more), but only a real Windows Chrome or Edge, with
`tools/web/shader_programs.js --build --level=...`, can say what the demo's wait would fall by. A Windows browser
translates WebGL to Direct3D, which compiles big branchy shaders at least as badly, so the saving is likely there.
Nothing drawn would change if every pattern a zone's meshes use
is kept: `PAT_*` references by file give each zone's set (City, Gangland: the base ids; Marketplace: 20s; Casino:
80s and three of the Marketplace's, in `casino_facades.gd`; Corporate: 30s; Dead Zone: 40s; Golden Zone: 50s;
Palace: 70s and the Golden Zone's; Beach: 90s; Hostile Takeover's props 30s, Golden Convergence's 50s and the
Palace's hole 70s).

It is not a cleanup that fits a non-core task, so it was not built. What it needs, and the owner's or the orchestrator's
call:
- The shader: wrap each zone's include and its dispatch line in `#ifdef KIT_<ZONE>` (the file's default, with no
  `KIT_LEAN`, defines them all, so every tool, test and prop that loads the file as now draws as before); a lean
  Shader is `Shader.new()` with `"#define KIT_LEAN\n#define KIT_MARKET\n" + code`, built once per zone key.
- Choosing it: `MeshKit.solid()` is a static call from some 35 places (every skin, the shared floor-cut, wall-gap
  and wall-fence looks in `zone_skin.gd`, `RubbleBurst`, the bosses' props) that knows no skin. Two ways: (a) a
  static "kit zone" that `RunWorld.build` sets from its skin (a one-line hook in a core file) and that swaps the
  Shader of every cached kit material in place (`MeshKit._materials`, so skins' own caches follow), reset to the
  full shader when a run ends (a stale lean shader in the next context is the one way it can draw wrongly; the full
  one is a superset, so a reset is always safe), and set by `CineStage` too; or (b) every skin hands its own
  material to its helpers (no global, but 35 edits, and a boss's props, which are `MeshKit.solid()` too, would then
  compile the full shader beside the arena's lean one unless they take the arena skin's variant).
- Guards: a test that every `PAT_*` a skin's or a boss's files name lies in the zone's set (cheap, by source), one
  that a level's materials hold a single kit shader (`tools/measure/zone_shaders.gd` already finds twins), and frames
  of each zone's first level before and after (a seeded quick-play frame is byte-identical run to run).

**The placeholder.** None built: every zone draws with the one shader, as before.

## 2. Draw the web build's opaque things without a depth pre-pass? (performance; no GDD section)

**The question.** The Compatibility renderer draws every opaque surface twice by default, a depth pre-pass and then
the colour pass (`rendering/driver/depth_prepass/enable`, on in `project.godot` by default; Godot already turns it off
on Mali, Adreno, PowerVR and Apple GPUs). Each opaque shader therefore compiles its pre-pass program(s) as well. On
the web, where every program is a wait at the level's load, switching it off gives the same image with fewer
programs: measured with the debug web export (software WebGL, `tools/web/shader_programs.js --level=`), City 1's load
compiles 123 programs instead of 135 and 13.8 M instead of 15.7 M characters of shader code (-12 programs, -12%), the
Golden Palace's 203 instead of 224 (-21, -11%). Opaque draws cost less on the CPU too (one pass instead of two). What
it can cost is GPU time on a desktop card: the street's heavy fragment shader (`kit_solid`) runs on every overlapping
opaque pixel instead of only the nearest, and software WebGL cannot show that. Should the build try it, on the web
only (a `web` feature override) or everywhere, with a frame-time check on a real GPU first?

**The placeholder.** None built: the setting stays at the engine's default (on). It is one line under `[rendering]`
(`driver/depth_prepass/enable=false`, or a `web.` feature override of it), so it is cheap to try and to take back.
